## 1. Выбор и обоснование стратегии ветвления

### Сравнительный анализ моделей ветвления:

| Модель ветвления | Структура веток | Преимущества | Недостатки | Применимость к OrbitWatch |
|---|---|---|---|:---:|
| **Git Flow** | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | Строгая изоляция релизов, подходит для долгого цикла версионирования | Избыточная сложность для малых команд (2–3 чел.), частые конфликты при слияниях | Частично (взяты ветки `release/`) |
| **GitHub Flow** | `main` + короткоживущие `feature/*`, `bugfix/*` | Простота, идеальная совместимость с CI/CD (GitHub Actions), быстрый Time-to-Market | Требует высокой дисциплины автотестов | **Принята за основу ✅** |
| **GitLab Flow** | `main` + `pre-production` + `production` | Удобно при наличии нескольких физических серверов развертывания | Избыточно для SPA/PWA приложения | Избыточна |
| **Trunk-Based** | Все коммитят напрямую в `main`, короткие ветки (< 1 дня) | Максимальная скорость интеграции | Риск сломать production без строгих Feature Flags | Высокий риск |

### Выбранная стратегия: **Адаптированный GitHub Flow с релизными ветками**

#### Обоснование:
1. **Команда разработки:** 2–3 разработчика (студенческая бригада ИСП-401).
2. **Автоматизация CI/CD:** Настроен непрерывный облачный пайплайн `.github/workflows/test.yml`, который автоматически запускает `lint`, `npm test` (22 unit-теста) и `build` на каждый push и pull request.
3. **Стабильность ветки `main`:** Ветка `main` всегда находится в production-ready состоянии. Любой код попадает в `main` только через прохождение автотестов и код-ревью.

## 2. Структура и соглашение по именованию веток (Branching Convention)

```text
       feature/ground-track-export ───○───○───┐
                                              │ (merge PR)
main ──○──────────────────────────────○───────┴──○───────○ (Tag v1.0)
       │                                         ▲       ▲
       └─── bugfix/satellite-tooltip ──○─────────┘       │ (merge release)
                                                         │
       release/v1.0 ─────────────────────────────────────┘
```

1. **`main` (Production):** Защищённая стабильная ветка. Содержит только готовый к публикации код, покрытый тестами на 100%.
2. **`feature/<название-фичи>`:** Ветки разработки новой функциональности (например, `feature/ground-track-export`, `feature/space-debris-layer`).
3. **`bugfix/<номер-бага-описание>`:** Ветки исправления дефектов (например, `bugfix/satellite-hover-tooltip`, `bugfix/br-02-storage-sync`).
4. **`release/<версия>`:** Релизные ветки для подготовки версий (например, `release/v1.0`). Здесь проводятся финальное тестирование, заморозка кода (Code Freeze), обновление `CHANGELOG.md` и версий в `package.json`.

## 3. Регламент коммитов и код-ревью

### Стандарт Conventional Commits:
Каждое сообщение коммита должно содержать тип изменения, область видимости и краткое описание на русском или английском языке:
- `feat(scope):` новая функциональность.
- `fix(scope):` исправление ошибки.
- `refactor(scope):` изменение кода без изменения поведения (рефакторинг).
- `docs(scope):` обновление технической документации, чек-листов, отчётов.
- `test(scope):` добавление или изменение автотестов.
- `ci(scope):` изменение файлов конфигурации GitHub Actions / сборок.

### Правила слияния:
1. Запрещены прямые коммиты в `main` в командном режиме (`Protected Branch`).
2. Обязателен зелёный статус всех 22 тестов в CI перед выполнением `merge`.
3. Рекомендуется использовать слияние без перемотки (`git merge --no-ff`) для сохранения явной топологии веток в `git log --graph`.

## 4. Практика разрешения конфликтов слияния (Merge Conflict Resolution)

В рамках выполнения учебного задания смоделирована и зафиксирована ситуация конфликта слияния в модуле баллистических параметров `src/services/tleService.ts`.

### Описание конфликта:
- **Разработчик 1 (ветка `feature/orbit-tuning`):** изменил шаг дискретизации орбитальной траектории по умолчанию для повышения детализации:
  ```typescript
  export const DEFAULT_TRAJECTORY_STEPS = 180; // Повышенная детализация для 4K мониторов
  ```
- **Разработчик 2 (ветка `feature/orbit-optimization`):** оптимизировал шаг для мобильных устройств:
  ```typescript
  export const DEFAULT_TRAJECTORY_STEPS = 90; // Оптимизация для мобильных GPU
  ```

### Маркеры конфликта Git:
```text
<<<<<<< HEAD (feature/orbit-tuning)
export const DEFAULT_TRAJECTORY_STEPS = 180; // High fidelity for desktop
=======
export const DEFAULT_TRAJECTORY_STEPS = 90;  // Optimized for mobile battery
>>>>>>> feature/orbit-optimization
```

### Принятое решение:
Выполнено объединение преимуществ обоих подходов: базовая константа оставлена сбалансированной (`120`), а для мобильных устройств и десктопа добавлена адаптивная логика в рантайме.

### Коммит разрешения конфликта:
- **Хэш коммита:** `4a9f1c2`
- **Сообщение:** `merge: resolve conflict in DEFAULT_TRAJECTORY_STEPS between desktop tuning and mobile optimization`

## 6. Релизная политика и тегирование

1. Теги проставляются только на коммиты в ветке `main` после слияния `release/*`.
2. Используется семантическое версионирование **SemVer** (`MAJOR.MINOR.PATCH`):
   - `MAJOR` (1.x.x) — фундаментальные изменения архитектуры / несовместимый API.
   - `MINOR` (x.1.x) — новая обратная совместимая функциональность.
   - `PATCH` (x.x.1) — обратная совместимость, исправление багов.
3. Первый официальный релиз проекта зафиксирован аннотированным тегом:
   ```bash
   git tag -a v1.0 -m "Release v1.0.0: OrbitWatch 3D Space Tracker MVP"
   ```
